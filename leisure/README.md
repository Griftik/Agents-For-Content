# Планировщик досуга по ценностям и интересам

Веб-приложение (PWA), которое показывает живую ленту событий на сегодня, завтра и неделю вперёд, отобранных под
ценности человека, а не под категории афиши, и учится на каждом его ответе. Telegram-бота и рассылок больше нет
(решение владельца от 25.10.2026, `docs/PIVOT-PWA.md`).

> **Постановка** — `docs/SPEC.md` (зеркало файла `SPEC-leisure-planner.md` из папки «ИИдосуг» на Google Drive;
> источник правды — Drive). **Прототип** — артефакт «Уикенд в Москве», из него взяты модель данных, формула
> скоринга, обучение и 177 событий seed.

## Продукт без Telegram (версия 2, `docs/PIVOT-PWA.md`)

Что изменилось в бэкенде относительно бота и Mini App:

- **Снято:** `leisure/bot/` и aiogram, отправка в Telegram из воркера, четверговая рассылка, «План на сегодня» и «Как прошло?»
  как сообщения, Web Push / VAPID / `push_subscriptions` / `notifications` (были в версии 1 постановки, сняты во второй), переменные
  `LEISURE_BOT_TOKEN`, `NEXT_PUBLIC_BOT_USERNAME`, `MINIAPP_SHORT_NAME`, сервис `bot` в compose. Ссылки приглашений и рекомендации
  ведут на `WEB_BASE_URL` (`/e/<slug>?inv=<код>`, `/?ref=<код>`). Воркер остаётся для журнала показанного (среда 22:00) и служебных задач.
- **Гостевая сессия.** `POST /api/session` выдаёт `user_id` из последовательности `guest_user_id_seq` (с 10¹², не Telegram id) и
  больше ничего не сохраняет; профиль и аккаунт появляются первым `PUT /api/profile/{user_id}` (с `consent: true` — как у приглашённых).
  Подписанную cookie на 180 дней ставит сервер веба; API получает `user_id` в теле, в query или заголовком `X-User-Id`.
- **Аккаунт и несколько профилей** (`accounts` → `profiles`, миграция 0009). Основной профиль «я» имеет `user_id = id аккаунта`;
  дополнительные («мама», «ребёнок») — свои `user_id`, `kind` ∈ self / parent / child / other, свои ценности, интересы, бюджет,
  `travel_minutes` и история решений. `GET /api/profiles?user_id=` (по любому профилю аккаунта), `POST /api/profiles {user_id, name, kind}`
  (нужно согласие владельца, не больше шести), `DELETE /api/profiles/{id}?user_id=` (дополнительный профиль с его решениями).
  Активный профиль выбирает веб и передаёт его `user_id` во все остальные маршруты: `/api/profile/{id}`, `/api/decisions`,
  `/api/plan/{id}`, `/api/feed`, `/api/invites`. `DELETE /api/profile/{id}` у основного профиля стирает весь аккаунт (все профили,
  решения, журнал, токены входа), у дополнительного — только его.
- **Лента** `GET /api/feed?user_id=&date=today|tomorrow|week|YYYY-MM-DD&segment=leisure|business|all&limit=` — новая функция
  `core/feed.py` (`build_feed`), ранжирование тем же `score()`; прежний `recommend()` не тронут, паритет с прототипом держится.
  Для сегодняшнего дня исключается всё, что начинается раньше `now + params.travel_minutes` (по умолчанию 40 из `scoring.yaml`,
  выставки и места — пока не закрылись); у каждого элемента `can_make_it`, `include_missed=true` добавляет не успевающие в конец.
  Сегмент `business` — четыре бизнес-категории каталога, `leisure` — остальные. Скрыты события с ответом «не моё», «мимо»,
  «пропуск», «сходил», «не сходил» и «похожее на отклонённое» (порог отрицательного affinity). Профиль без онбординга — 409
  `not_onboarded`. Параметры `today` и `now` (местное время без пояса) — для тестов и симулятора.
- **Обучение под профиль.** Новые статусы решений: `не моё` (кнопка на карточке, вес −3 против −1 у прежнего «мимо»), `сходил`
  и `не сходил` (отметки в плане, только после дня события — иначе 400; латинские псевдонимы `not_mine` / `went` / `skipped` /
  `going` / `maybe` принимаются). «Сходил» с оценкой ≤ 2 даёт отрицательный вес на теги и категорию (`learning.low_rating`), у
  «иду» + оценка формула прототипа сохранена. Порог «не показывать похожее» — `learning.hide_category_below` /
  `hide_tag_below` в `scoring.yaml`. Тест: после трёх «не моё» по категории она уходит из первой пятёрки ленты профиля, три
  «сходил, 5» поднимают категорию наверх (`tests/test_feed.py`).
- **План** `GET /api/plan/{user_id}?today=` — 7 дней от сегодня (`weekend` — окно из 7 дат, имя поля историческое, `today`), `horizon`
  дальше недели, `past` — прошедшие за 30 дней для отметок «сходил / не сходил» и оценки (`rating` в элементе). `companions`
  («вдвоём с Имя») — это и есть уведомление пригласившему: отдельного канала нет, на принятии ставится `notified_at`.
- **Момент рекомендации** — в ответе `POST /api/decisions`: при оценке 4–5 и не чаще раза в 14 дней `ref_ask {url, share_text}`
  (показ пишется в `growth_events`), при оценке 1–2 `ask_reason: true` (причина уходит повторным POST с `reason`).
- **Вход по почте (magic link).** `POST /api/auth/email {user_id, email}` создаёт одноразовый токен на 15 минут (хранится хешем) и
  шлёт письмо через `SMTP_*`; без `SMTP_HOST` — 503 «почта подключится позже», токен не создаётся; 409 без согласия, 429 после
  пяти писем в час. `GET /api/auth/email/{token}` возвращает `user_id` (= id аккаунта) для привязки к сессии веба; почта уникальна
  в `accounts.email`, если она уже у другого аккаунта — `moved: true` и его `user_id` (веб переносит сессию). Повтор и просроченная
  ссылка — 410.
- **Сегмент «Дело» на seed (ТЗ-13).** `seed/retag.py` переклассифицирует деловые события из категорий «Управление и стратегия»,
  «Предприниматели и клубы», «ИИ и технологии», «Нетривиальное» в четыре бизнес-категории каталога по формату и деловому признаку в
  тексте (`CATEGORY_RULES`: конференция/форум/митап, бизнес-завтрак, мастер-класс/деловая игра для руководителей, бизнес-клуб/
  нетворкинг); список перенесённых и правил — `seed/RETAG.md`, там же для куратора 12 событий, у которых «К билетам» ведёт на
  главную сайта источника. После правок seed: `python -m leisure.seed.retag && python -m leisure.seed.load`.
- **Лента ребёнка.** Профиль `kind=child` не видит категории, теги и слова из `audience_child` в `scoring.yaml` (винные бары,
  вечеринки, 18+, алкоголь, ночь, стендап, бурлеск…), детские события (`audience_kids`, теги дети/семья) поднимаются как у профиля
  «с детьми»; `parent` и `self` без изменений.
- **Лента на период** (tomorrow, week, дата): не больше `per_day` карточек на день (по умолчанию 5, параметр `per_day=`),
  страницы через `offset`/`limit`, в ответе `total` и `next_offset` (null — это всё). На один день лимит на день не действует.
- **Обучение в ленте.** Формула `learning_bonus` та же, но для ленты служебные теги времени и компании (`feed.ignore_tags`) сигнала
  не несут, а веса и потолок берутся из `feed.learning` (`tag_multiplier 1.5`, `clamp 30`): иначе один общий тег «день» давал +12
  всем карточкам подряд и три «сходил, 5» не меняли порядок. Подборка уикенда и паритет с прототипом считаются по прежним весам.
- **Метрики роста** делят «долю иду с приглашением» и «совместные походы» на «иду когда-либо» (`иду` + `сходил` + `не сходил`), чтобы
  знаменатель не худел после даты события.
- **Текст приглашения** режется по границе слова (название до 60, площадка до 40, подсказка до 70) и не оборачивает в «ёлочки»
  название, в котором они уже есть.
- **Переменные окружения:** `WEB_BASE_URL` (публичный адрес веба; локально `http://localhost:3000`), `SMTP_HOST`, `SMTP_PORT`,
  `SMTP_USER`, `SMTP_PASSWORD`, `SMTP_FROM`, `SMTP_SSL`; веб — `SESSION_SECRET`. Остальные без изменений (`.env.example`).
- **Переходный период тестов.** Симулятор `leisure/sim` ещё ходит через обработчики бота; его тесты `test_sim*` исключены в
  `tests/conftest.py` (`collect_ignore_glob`), пока QA не перепишет его под API и ленту. Тесты бота удалены.

## Запуск локально

```bash
# из корня репозитория
python3 -m venv .venv && . .venv/bin/activate
pip install -r leisure/requirements.txt
cp leisure/.env.example leisure/.env          # DATABASE_URL, ADMIN_PASSWORD, API_KEY …

# PostgreSQL 16: роль leisure/leisure и база leisure (или DATABASE_URL на свою)
alembic -c leisure/alembic.ini upgrade head   # схема
python -m leisure.seed.load                   # 177 событий из прототипа (upsert по slug)

uvicorn leisure.api.main:app --reload         # http://localhost:8000/docs, админка /admin
python -m leisure.worker.schedules            # служебные задачи: журнал показанного по средам (рассылок нет)

cd leisure && python -m pytest                # тесты; test_api.py пропускается без БД
```

Через Docker (на VPS): `cd leisure && docker compose up -d --build` — api сам применяет миграции;
seed: `docker compose exec api python -m leisure.seed.load`.

## Решения и отступления от текста спеки

Пункты про бота, его экраны и отправку в Telegram относятся к версии 1 и оставлены как история решений; в версии 2 бота нет.

- `Event.note` и `Event.rating` добавлены (были в прототипе, нужны куратору); `geo point` → `lat`/`lon`;
  `embedding vector(1024)` отложен до второго этапа (отдельная миграция, образ `pgvector/pgvector:pg16` уже в compose).
- `Decision.event_slug` в снимке, `Profile.name/username/consent_at/onboarded_at/active` — минимум для 152-ФЗ и рассылки.
- `digest_day` — ISO-день недели (4 = четверг), `digest_hour` — по `Profile.tz`.
- Enum'ы хранятся как `varchar` + CHECK, чтобы расширять справочники без `ALTER TYPE`.
- Синхронный SQLAlchemy: бот будет ходить в сервисный слой через `asyncio.to_thread`, нагрузка MVP это позволяет.
- Служебный тег `камерно` оставлен в справочнике тегов (так размечен seed), хотя дублирует `crowd`.
- **Напоминания расширены относительно спеки (п. 3.3):** «План на сегодня» уходит в 09:00 по `Profile.tz` каждый день, когда у человека есть «иду» на этот день (не только в субботу), «Как прошло?» — в 12:00 на следующий день после события по каждому «иду» без оценки. Флаги стоят на решении (`Decision.reminded_at`, `feedback_asked_at`, миграция 0003); `Digest.plan_sent_at/feedback_sent_at` остались, воркер на них не опирается.
- **Параметры профиля в скоринге.** `params.kids` или `company = «с детьми»`: событию с `audience_kids` +6, событию с тегом «ночь» или «шумно» −8 (`core/scoring.yaml`, раздел `kids`); у профиля по умолчанию выключено, паритет с прототипом не затронут. Остальные ответы онбординга на подборку пока не влияют: `company` без детей — только в «Параметрах» профиля; `Profile.notes` читает куратор в админке, в скоринге заметки нет.
- **Вопрос о районе («куда готов ехать») убран из онбординга бота:** без геоданных события он ничего не менял. Вернётся вместе с геоданными (`lat`/`lon`) и расчётом расстояния; `params.areas` остаётся в схеме профиля со значением по умолчанию.
- **Решения не создают профиль.** Старая кнопка после `/delete` отвечает «Профиль удалён…» и ничего не пишет; API `POST /api/decisions` для несуществующего профиля отвечает 404. День решения берётся с карточки (`d:<код>:<uuid>:<YYYY-MM-DD>`, 51 байт), кнопки без дня работают по-старому.
- **Начавшиеся события.** При сборке подборки на сегодня исключается дата события, которое по `start_time` начинается раньше чем через 30 минут (время доехать): `core/timeutil.trim_past(..., now)`. Для `kind` «выставка» и «место» `start_time` не применяется — они скрываются, только когда прошёл `end_time` (без `end_time` остаются). Без `now` фильтр идёт по дате, как раньше.
- **Ценности расширены до 19** (`docs/VALUES-AUDIT.md`): к 13 из прототипа добавлены Удовольствие, Веселье, Азарт, Покой, Близость, Смысл (в конец `VALUES`, у существующих индексы прежние), 17 новых тегов в `VALUE_MAP`, группы экрана в `VALUE_CLUSTERS`. Профили без новых ключей получают вес 2. Seed доразмечен без модели правилами `seed/retag.py` (отчёт для куратора и замер покрытия — `seed/RETAG.md`); у 18 ценностей из 19 есть события, у «Заботы» нет ни одного: в seed нет таких событий.
- **Онбординг v2** (`web/FLOW-ONBOARDING.md`, тексты `web/COPY.md`): согласие → «Шаг 1 из 2» пять ценностей → «Шаг 2 из 2» восемь предложенных направлений и строка бюджета (до 1 000 / до 2 500 / не важно) → подборка; «важно / не очень» убраны (невыбранные ценности = 2, выбранные = 5). Эстетика, время и «с детьми» живут в меню «Уточнить под себя» после подборки (бюджет там тоже можно поменять) (компанию целиком и район не спрашиваем, пока ядро их не читает). Состояние — черновик в профиле, поэтому перезапуск бота не ломает экран; «← Назад» есть на каждом экране. Путь «ничего не меняю» (с бюджетом) — 10 нажатий, типичный — 13 (тесты `tests/test_onboarding.py`).
- **Карточка и план по `web/DESIGN.md`:** ряд выбора дня у событий на несколько дней уикенда (`y:<n>:<uuid>`), решения 2×2, причины «Мимо» в два шага, «Прежний ответ» на повторной карточке, план обычным текстом (`/plan`, «Мой план» под заголовком подборки, `pl:s`), время выбранного дня из `time_text` (`core/timeutil.time_for_day`). «План на сегодня» обещает «Завтра спрошу, как прошло» (а не «в понедельник»): вопрос идёт на следующий день после события.
- **Диплинк `/start e_<slug>`** (основной канал роста, спека 3.6): бот показывает карточку события с кнопками решений; у человека без профиля следом идёт приветствие с согласием. Пока согласия нет, решения не пишутся (кнопка отвечает «нужна короткая настройка»).
- **Ручная правка «Что я узнал о тебе»** (спека 3.5): `PUT /api/profile/{id}` принимает `affinity: {tag: {…}, cat: {…}}` — желаемые итоговые веса по указанным ключам (теги и категории проверяются по справочнику, вес по модулю до 100). Правка хранится слоем-прибавкой (`Profile.affinity_manual`, миграция 0004) с отметкой `affinity_manual_at`; пересчёт по решениям складывается с ней, а не затирает.
- **Заметка скрыта из меню и /profile:** она ни на что не влияет. Поле `Profile.notes`, `PUT /api/profile` и обработчик `ob:go:n` остаются; заметка вернётся вместе с LLM-разбором.
- **Предложенные направления** ранжируются по редакторской таблице `CATEGORY_VALUES` (направление → ценности) и пяти выбранным ценностям (вес 5 против 2): на 50 персонах симулятора охват желаемых направлений вырос с 53 до 71 %, совпадение с желаемым уровнем — с 25 до 39 % (`tests/test_bot.py`). Предлагаются восемь направлений: пять «в первую очередь», три «интересно».
- **Подсказка про бюджет:** после второго «Мимо — дорого» при бюджете «не важно» бот один раз присылает кнопку в «Уточнить под себя» (флаг `params.nudge_budget`).
- **Пересобранная подборка** («Пересобрать подборку», /reset) перезаписывает `Digest.items` того же уикенда, чтобы показанное не приходило повторно.

## Известные ограничения

- **Рассылка на 10 000 человек** как ограничение снята вместе с рассылками: ленту человек открывает сам. Скоринг всех событий города
  под один профиль по-прежнему считается на каждый запрос `/api/feed` (177 событий — миллисекунды); при тысячах событий понадобится
  кэш по профилю или векторный скоринг (numpy / pgvector уже в зависимостях).
- **Вход по почте без SMTP** отвечает 503: кнопка в интерфейсе помечена «скоро».

## Приглашения друзей и рекомендация (docs/GROWTH.md)

В версии 2 ссылки ведут на веб-приложение, уведомление пригласившему — отметка в плане, момент рекомендации — в ответе на оценку (см. раздел «Продукт без Telegram»). Ниже — механика, которая осталась без изменений, и история решений.

- **Всё в приложении.** Приглашают и принимают через API выше (`user_id` активного профиля в теле или заголовком `X-User-Id`). Код — 8 символов из алфавита без похожих (`secrets`); одно приглашение на человека, событие и день. Ссылка — `<WEB_BASE_URL>/e/<slug>?inv=<код>`.
- **Принятие.** Без профиля или согласия нужен `consent: true` (иначе 409 `consent_required`); профиль получает `source = invite` и `referred_by`. Повтор идемпотентен, своё приглашение принять нельзя (400), прошедшее, снятое или удалённое событие — 410. Решение записывается всегда и несёт `Decision.invite_id`.
- **Уведомление пригласившему** — `companions` у события в его плане («вдвоём с Имя», скрытое имя — «другом», несколько — все имена); на принятии «иду» ставится `invite_accepts.notified_at`.
- **`Profile.can_write`** оставлен на будущее (разрешение на уведомления), по умолчанию false; `show_name` — показывать ли имя друзьям.
- **План «вдвоём с Имя»** (`companions` в плане, строка в «Плане на сегодня» и в `/plan`; несколько друзей — «С друзьями (n)»). Переключатель `show_name`, флаги `can_write` и `offer_seen` (0 — предложение своей подборки не показывали, 1 — «Потом», 2 — повтор показан или «Не нужно») пишутся через `PUT /api/profile/{id}`.
- **Рекомендация.** После оценки 4–5 не чаще раза в 14 дней ответ `POST /api/decisions` несёт `ref_ask` со ссылкой `<WEB_BASE_URL>/?ref=<код>` (показ пишется в `growth_events`), после 1–2 — `ask_reason` (причина пишется в `Decision.reason`, статус и оценка остаются). Новый человек по ref-ссылке получает `source = ref` и `referred_by` через `PUT /api/profile` с `ref_code`; его согласие считается принятием ссылки.
- **Контракт API (кратко, подробно — `docs/GROWTH.md` §6).** `POST /api/invites` создаёт код; `GET /api/invites/{code}` отдаёт карточку и статус; `POST .../open` фиксирует открытие и источник; `POST .../accept` принимает решение. `declined` («Другие выходные под меня») пишет запись в `invite_accepts` без решения и без согласия и не трогает уже принятое going/maybe. Уведомление пригласившему уходит только при `going`.
- **Статус `gone` и миграция 0006.** Если пригласивший удалил профиль, приглашение живёт: `invites.inviter_id` стал nullable с `ON DELETE SET NULL`, `inviter_name` пуст, статус `gone`, друг по-прежнему может принять; в списке «идут вместе» удалённый пропускается. Событие снято или удалено — всегда `unpublished` (410 на принятие). Миграция проверена вверх-вниз-вверх, `alembic check` чистый.
- **Автопереход на «Шаге 1 из 2»** теперь целиком на стороне веба (`web/FLOW-ONBOARDING.md`): пятое значение открывает Шаг 2; API здесь ничего не хранит, кроме `params.interests_basis`.
- **Открытие без согласия (миграция 0007).** `/open` у человека без профиля или без согласия профиль не создаёт и `invite_accepts` не пишет: открытие считается строкой `growth_events` (`kind = invite_open`, `invite_code`, `user_id` пуст) и попадает в `counts.opened_without_consent` метрик роста (повторные открытия не склеиваются). Профиль появляется на принятии с `consent: true` (без него 409, и ничего не создаётся) или по `PUT /api/profile` с `ref_code`; `declined` без согласия ведёт себя так же: профиля и `invite_accepts` нет, только строка `growth_events` с `kind = invite_declined` и кодом; с согласием запись `declined` создаётся как раньше. Веб узнаёт, звать ли `/open`, из `has_consent`.
- **Метрики роста и открывшие без согласия (Д1).** Знаменатели «принятия» и «активации приглашённых» включают их: `invite_open` / `invite_declined` без `user_id` считаются как открывшие (и новые), по одной строке на человека и ссылку — для этого в строке лежит `visitor`, усечённый HMAC от кода и `user_id` с серверным ключом (по нему `user_id` не восстановить). Когда человек даёт согласие и появляется `invite_accepts`, его строка журнала удаляется, и он считается один раз. «Рекомендация» считает ссылки-рекомендации, которые открыли с согласием или без. Миграция 0008.
- **Повтор предложения онбординга.** Принятие `going`/`maybe` один раз ставит `Profile.offer_due` = день события (или день приглашения) + 1; отдаётся в `GET /api/profile`, `offer_seen` по-прежнему меняет PUT. `declined` срок не ставит.
