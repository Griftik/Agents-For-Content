# Команда проекта и регламент работы

Продукт делает маленькая команда агентов под оркестровкой. Роли описаны машиночитаемо в
`.claude/agents/leisure-*.md`: оттуда берутся модель, инструменты и правила роли, так что команду можно собрать
заново в любой сессии.

## Состав

| Роль | Файл роли | Модель | За что отвечает | Зона файлов |
|---|---|---|---|---|
| **Оркестратор** | — (ведущая сессия) | Opus 5 | постановка задач, приёмка, спорные решения, коммиты и пуш, связь с владельцем продукта и Drive | весь репозиторий |
| **Бэкенд** | `leisure-backend.md` | Sonnet | ядро скоринга, API, модели и миграции, воркер, бот | `core`, `api`, `db`, `worker`, `bot`, `normalize`, `seed`, `tests` |
| **QA и симуляция** | `leisure-qa.md` | Sonnet | прогон пользователей через настоящие обработчики, метрики, доказательства по юзабилити | `sim`, `tests/test_sim*.py` |
| **Дизайн и тексты** | `leisure-design.md` | Sonnet | дизайн-система, экраны Mini App, формулировки интерфейса, разбор юзабилити | `web`, канвас макетов |
| **Данные** | `leisure-data.md` | Sonnet | коллекторы источников, LLM-нормализация, дедупликация, качество данных | `collectors`, `normalize`, `seed` |

### Почему такие модели

Оркестратор держит в голове постановку, историю решений и приёмку — это самая дорогая по контексту работа, её
ведёт сильная модель. Исполнители получают узкое ТЗ, свою зону файлов и измеримый критерий приёмки, поэтому им
хватает Sonnet: тяжёлый контекст (большие JSON, диффы, логи прогонов) остаётся у них и не попадает в основную
сессию. Механические проверки по одному файлу можно отдавать Haiku, но отдельной роли под это нет: такие задачи
дешевле делать внутри уже запущенного агента.

## Зоны файлов

У каждого файла один владелец. Это главное правило: агенты работают в одной ветке, и пересечение зон — почти
гарантированный конфликт. Чужая зона доступна только на чтение.

Исключения, которые нельзя менять никому, кроме оркестратора:
`leisure/docs/SPEC.md` (зеркало постановки с Google Drive), `.claude/agents/**`, `leisure/docs/TEAM.md`.

## Поток работы

1. **Постановка.** Оркестратор пишет ТЗ: контекст, задача по пунктам, зона файлов, правила, критерий приёмки и
   что вернуть. Без критерия приёмки задача не ставится.
2. **Исполнение.** Агент работает в своей зоне, прогоняет тесты, возвращает короткий отчёт. Подробности остаются
   в файлах репозитория, а не в отчёте: так контекст оркестратора не раздувается.
3. **Приёмка.** Оркестратор проверяет сам, а не по словам отчёта: читает диff, прогоняет тесты, сверяет со
   спекой. Что не сошлось — уходит в ТЗ на доработку тому же агенту (продолжением, с сохранённым контекстом).
4. **Фиксация.** Коммит и пуш делает оркестратор одним осмысленным коммитом на задачу.
5. **Статус.** После заметного этапа оркестратор обновляет заметку о статусе в папке «ИИдосуг» на Google Drive.

## Правила, общие для всех

- Постановка важнее вкуса: отклонение от спеки допустимо, только если оно записано в `leisure/README.md`.
- Дефект без теста считается неисправленным.
- Красный набор тестов не сдаётся. Полный прогон: `cd leisure && python -m pytest`.
- Числа скоринга меняются только через `core/scoring.yaml`; паритет с прототипом (`tests/test_prototype_parity.py`)
  остаётся зелёным.
- Секреты не попадают ни в код, ни в логи, ни в образ.
- Тексты интерфейса — по-русски, ты-обращение, тон прототипа.
- Симулятор (`leisure/sim`) пересоздаёт общие тестовые базы `leisure_sim` и `leisure_sim_smoke`: пока один агент
  его гоняет, остальные исключают `tests/test_sim_smoke.py` из своих прогонов, иначе прогоны сталкиваются на базе.
- Тесты с базой берут id пользователей из `tests/ids.py` (уникальны на процесс) и создают свои события, а не
  переключают seed: параллельные прогоны разных агентов не должны видеть друг друга.
- Коммит промежуточного снимка допустим только при зелёном наборе; сводку pytest читать по строке «N passed»,
  а не по коду выхода конвейера (двойной `-q` её скрывает).

## Приёмка по ролям

| Роль | Чем подтверждается работа |
|---|---|
| Бэкенд | зелёный полный прогон тестов; новый тест на каждый закрытый дефект; миграция прогнана вверх и вниз |
| QA | воспроизводимый прогон симулятора, `sim/REPORT.md` с метриками против целей п. 11 спеки |
| Дизайн | обновлённые `web/DESIGN.md` и канвас; предложения с ожидаемым эффектом на метрику |
| Данные | число событий с источника, доля «подтверждено», найденные дубликаты, тест на сохранённом фрагменте |
