# Поворот: отдельное веб-приложение (PWA) вместо Telegram-бота

Решение владельца продукта (25.10.2026): «ботом пользоваться никто не будет». Продукт становится отдельным
веб-приложением, которое ставится на экран телефона (PWA). Telegram из продукта уходит целиком: нет чата, нет
Mini App, нет входа через Telegram. Этот документ заменяет разделы спеки про бота и `docs/GROWTH.md` в части
Telegram; ядро скоринга, данные, метрики п. 11 и механика приглашений остаются.

## 1. Что меняется и что нет

| Остаётся | Уходит | Появляется |
|---|---|---|
| ядро, 19 ценностей, seed, коллекторы, API, админка | `leisure/bot/`, отправка через aiogram в воркере, initData, Mini App, `startapp`, `can_write` | PWA: manifest, service worker, установка на экран |
| онбординг в два шага (уже есть в вебе) | кнопки решений в чате, «План на сегодня» и «Как прошло?» в чате | те же сообщения как push-уведомления и экран «Входящие» в приложении |
| приглашения: страница «Имя зовёт тебя», 3 нажатия до «иду» | ссылки `t.me/…`, уведомление в чат | ссылки `<домен>/e/<slug>?inv=<код>`, уведомление push + «Входящие» |
| момент рекомендации после оценки 4–5 | сообщение бота | экран в приложении после оценки, системное «Поделиться» |
| симулятор и метрики | обработчики aiogram в симуляторе | симулятор ходит через API и канал push |

## 2. Вход без пароля и без провайдеров

Внешних провайдеров (SMS, Google, Telegram) на MVP нет: каждый требует регистрации у владельца. Поэтому:

1. **Гостевой аккаунт с первого экрана.** Открыл ссылку — уже пользователь: сервер выдаёт `user_id` и подписанный
   httpOnly-cookie сессии на 180 дней. Онбординг, решения, приглашения работают сразу. Согласие на обработку
   данных — галочка на первом экране (как сейчас на странице приглашения), до неё ничего не сохраняется.
2. **Привязка почты, по желанию.** «Чтобы не потерять подборку на другом телефоне» — вводишь почту, получаешь
   ссылку-вход (magic link, 15 минут, одноразовая). Требует SMTP от владельца; до него кнопка в интерфейсе есть,
   но помечена «скоро», письма не уходят.
3. **Удаление.** «Удалить мои данные» в профиле стирает профиль, решения, подписки на push — как `/delete` раньше.

Идентификатор человека в API — `user_id` из сессии (как сейчас через заголовок сервера веба), ключ API остаётся
серверным.

## 3. Уведомления

- **Web Push** (VAPID; ключи генерируем сами, провайдер не нужен). Работает в Chrome/Android и в Safari/iOS 16.4+
  для приложения, установленного на экран. Разрешение спрашиваем не на старте, а в момент пользы: после первой
  подборки («Присылать подборку по четвергам?») и после первого «иду» («Напомнить утром в день события?»).
- **Экран «Входящие»** в приложении дублирует каждое уведомление: кто не дал разрешение или зашёл с десктопа,
  видит то же самое внутри. Это основной канал, push — ускоритель.
- **Почта** (когда будет SMTP): четверговая подборка письмом как второй канал, по выбору.
- Сообщения те же четыре: «Подборка на выходные готова», «Сегодня идёшь: …», «Как прошло?», «Имя идёт с тобой».
  Тексты — `web/COPY.md`, заменяя T-бота на push-варианты (заголовок до 40 знаков, тело до 100).

## 4. Экраны приложения (мобильный первый, нижняя навигация)

| Вкладка | Что | Откуда берётся |
|---|---|---|
| Подборка | 5 слотов на выходные + «на горизонте», кнопки решений, фильтры | `/digest` уже есть |
| План | по дням, конфликты, календари, «вдвоём с Имя», «Позвать друга» | `/plan` уже есть |
| Входящие | уведомления и «Как прошло?» с оценкой, момент рекомендации | новое |
| Профиль | ценности, направления, бюджет, «что я узнал», почта, push, удалить данные | `/profile` уже есть |

Первый вход: приветствие с галочкой согласия → Шаг 1 (пять ценностей, авто-переход) → Шаг 2 (восемь направлений,
бюджет) → подборка → мягкое предложение установить на экран (после второго визита или первого «иду»).
Пути: 9 и 12 нажатий, как в `web/FLOW-ONBOARDING.md`; приглашённый до «иду» — 3.

## 5. Что делает каждая роль

1. **Оркестратор**: этот документ, README, TEAM.md (роль «бот» снимается), статус на Drive.
2. **Бэкенд**: сессии гостевого аккаунта (`POST /api/session` выдаёт `user_id` + токен для cookie веба; веб хранит
   секрет подписи у себя, как сейчас), `push_subscriptions` (endpoint, ключи, user_id), отправка push в воркере
   через `pywebpush` вместо aiogram, `notifications` (входящие: тип, текст, ссылка, прочитано), magic link
   (`POST /api/auth/email`, `GET /api/auth/email/<token>`, письма через SMTP-настройки, без SMTP — 503 с понятным
   текстом), удаление `bot/` и Telegram из воркера и моделей (`telegram_id` → `user_id` остаётся числом, `source`
   без `share`-через-бота), миграция 0009, ссылки приглашений на `WEB_BASE_URL`. Тесты бота удаляются, остальное
   зелёное; паритет держится.
3. **Веб**: PWA (manifest, иконки, service worker с push и офлайн-заглушкой), гостевая сессия с первого экрана и
   согласие, подписка на push в моменты пользы, вкладка «Входящие», оценка «Как прошло?» и момент рекомендации
   в приложении, привязка почты, удаление данных, нижняя навигация, удаление Telegram SDK и `startapp`;
   приглашения по обычным ссылкам с Web Share API. Сквозная проверка `scripts/e2e-*.mjs` на настоящем API.
4. **Дизайн**: `web/FLOW-APP.md` (первый вход, разрешение на push, установка на экран, входящие, оценка,
   рекомендация), `COPY.md` (push-тексты, экран входящих, почта, удаление), `DESIGN.md` (нижняя навигация,
   без ограничений Telegram), макет.
5. **QA**: симулятор ходит через API (гостевая сессия → онбординг → решения → приглашения) и фейковый канал push
   (принял/отклонил разрешение, открыл уведомление); метрики п. 11 и GROWTH §4 без изменений; новая метрика —
   доля давших разрешение на push и доля открывших уведомление.

## 6. Что зависит от владельца

Домен с HTTPS (push и установка на экран без него не работают; локально — `localhost`), SMTP для писем,
сервер. Ключи VAPID генерируем сами и кладём в `.env`.

# Версия 2 (25.10.2026, уточнение владельца): живая лента, а не рассылка

Владелец уточнил продукт голосом. Главное:

1. **Никаких рассылок и уведомлений как основы.** Человек сам открывает приложение, и оно всегда актуально:
   рекомендации на сегодня, завтра, послезавтра, неделю вперёд. Push и «Входящие» из версии 1 **снимаются**
   из MVP (инфраструктуру не строим; вернёмся, если спрос покажет).
2. **Сценарий «освободился вечер».** Открыл приложение → «Сегодня» → видны 3–5 событий, на которые ещё успеваешь
   (старт не раньше, чем через время на дорогу), быстро выбрал, нажал «Иду», получил ссылку на событие
   (оплата у источника; свою оплату делаем потом).
3. **Выбор по датам и направлениям.** Сверху — дни (Сегодня · Завтра · Послезавтра · Неделя · календарь), ниже —
   направление (Досуг · Дело · Всё), внутри — ранжирование по ценностям и интересам профиля с весами.
   Рекомендации на каждый день, не только на выходные.
4. **Несколько профилей в одном аккаунте**: «я», «мама», «ребёнок». У каждого свои ценности, интересы,
   бюджет и своя история решений. Переключатель профиля в шапке.
5. **План и обучение под конкретного человека.** В плане отмечаешь «сходил / не сходил» и оценку; модель
   этого профиля учится: то, что отмечено «не моё» или получило низкую оценку, уходит вниз и больше не
   всплывает в похожем виде; то, куда сходил с высокой оценкой, усиливает веса. Обучение персональное,
   не общее.
6. **Интерфейс нативный и красивый, без объяснений.** Никаких текстов «почему мы так считаем», никаких
   пояснений про цвета. Карточки событий как лента рекомендаций (ориентир — Tinder/Afisha по ощущению:
   крупная карточка, одно действие на экран), мобильный первым, 95 % трафика с телефона. В будущем — App Store,
   сейчас — установка на экран.

## Экраны v2 (нижняя навигация из трёх вкладок)

| Вкладка | Что |
|---|---|
| **Рекомендации** | дни сверху, направление, лента крупных карточек: фото/обложка (если есть), название, время, место, цена, бейдж «успеваешь»; действия «Иду» и «Не моё» (свайп или кнопки), «Подробнее» → страница события с кнопкой на источник и «Позвать друга» |
| **План** | по дням, прошедшие события с отметкой «сходил / не сходил» и оценкой ★1–5, «вдвоём с Имя», календари |
| **Профиль** | переключатель профилей (я · мама · ребёнок · +), ценности и направления с весами как ползунки/чипы, бюджет, время, «что я о тебе узнал» (теги и категории с плюсом и минусом, можно подправить), почта, удалить данные |

Первый вход: согласие галочкой → пять ценностей → восемь направлений и бюджет → лента на сегодня. 9–12 нажатий.

## Ядро и API v2

- `GET /api/feed?profile_id&date=YYYY-MM-DD|today|tomorrow|week&segment=leisure|business|all&limit=` — ранжированные
  события на день или период с баллом; для сегодня исключается всё, что начинается раньше now + `travel_minutes`
  (из профиля, по умолчанию 40), бейдж `can_make_it`. Паритет со старым `recommend()` сохраняется для тестов,
  но продукт использует ленту.
- Сегмент: `business` = четыре бизнес-категории каталога, `leisure` = остальные.
- Аккаунт и профили: `accounts` (сессия) → `profiles` (несколько на аккаунт: `name`, `kind` self/parent/child/other,
  свои ценности/интересы/параметры), решения привязаны к профилю. `POST /api/profiles`, переключение в сессии веба.
- Обучение: решения `went` / `skipped` (после даты события) и `rating` усиливают `affinity` профиля; «Не моё» на
  карточке — отрицательный вес сильнее, чем прежний «мимо»; низкая оценка ≤ 2 — отрицательный вес на теги и
  категорию; правило «не показывать похожее» = порог отрицательного affinity в `scoring.yaml`. Веса обучения
  поднимаются в `scoring.yaml`, формула не меняется; QA проверяет на персонах, что после трёх «не моё» по
  категории она исчезает из первой пятёрки.
- Приглашения: как в разделе 2 версии 1, по обычным ссылкам. Уведомление пригласившему — отметка в плане
  («Имя идёт с тобой»), без push.

## Что снимается из версии 1

Push, VAPID, `push_subscriptions`, `notifications`/«Входящие», четверговая рассылка как сущность (воркер
остаётся для сбора событий и для служебных задач), запрос разрешения на уведомления, письма-дайджесты.
Остаётся: гостевой аккаунт, magic link по желанию, удаление данных, PWA-установка.
